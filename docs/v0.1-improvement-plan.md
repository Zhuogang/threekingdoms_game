# Hegemony of the Three Kingdoms — v0.1 improvement plan

**Status:** implemented and technically verified October 19, 2026; independent human usability acceptance pending. See [validation](validation.md) and the [acceptance record](v0.1-improvement-acceptance.md) for delivered results.
**Updated:** October 19, 2026.

**Working branch:** `hegemony_of_the_three_kindoms_v0.1`.

**Intended implementation agent:** GPT-6.1 Sol, with this document as its handoff.

**Release:** retain application version `0.1.0` and the existing v0.1 branch.

This document supersedes the earlier conversational improvement plan. In particular,
**headshots are mandatory for every named officer, not an optional pilot**. All milestones below
are required for completion. A fallback image is error handling, not completed portrait coverage.

The goal is a more readable, recognizable, and understandable game without replacing its rules or
architecture. Improve the existing playable game through bounded changes, with evidence for each
acceptance criterion. Values labeled **required** are release gates. Values labeled **tuning target**
guide investigation and must not be reported as proven guarantees of fun or balance.

Track two results separately: **technical implementation verified**, which requires all milestone
technical gates, and **independent human usability acceptance**, which requires actual player
feedback. A coding agent must finish the technical work even if an independent player is not
available, then explicitly report that usability acceptance is pending. That status does not
relax portrait coverage or any required correctness, visual, or persistence check.

## 1. Product outcome and scope

The completed update must let the player:

1. Read the map, battlefield, numbers, and controls comfortably on a laptop or HD monitor, and
   choose a larger presentation at any time.
2. Recognize an officer through a distinct headshot, family-name banner, full name, and current
   allegiance.
3. Distinguish all six troop classes and tell which commanders can still act.
4. Choose how readily rivals start wars and understand what that setting does.
5. Read a useful account of rival activity after a month resolves.
6. Continue an existing v0.1 campaign, including a battle interrupted by a reload, without losing
   or duplicating progress.
7. Use every new feature in English or Simplified Chinese.

### Scope boundaries

- Keep TypeScript, React, PixiJS, Vite, Zod, IndexedDB, and the existing test tools.
- Keep the current scenario: 24 cities, 52 named officers, six playable factions, and six troop
  classes. Keep the logical 12 × 10 battlefield.
- Keep combat formulas, movement and range rules, campaign economy, and tactical AI unchanged.
  Campaign attack policy changes are limited to Milestone 4.
- Keep the current authored atlas. Improve its presentation; do not replace geography, city
  coordinates, adjacency, or historical boundaries in this update.
- Do not add multiplayer, accounts, cloud saves, a backend, mobile/native builds, new scenarios,
  a new state library, an ECS, or a broad directory reorganization.
- Do not introduce AI personalities, strategic transport planning, or new diplomacy behavior.
- Keep all existing save routes and the always-available language switch.
- Do not rename stable officer IDs, troop IDs, save keys, database names, or the ruleset as cosmetic
  cleanup.

## 5. M1 — Readability and camera

### Display presets

Add **Compact / 紧凑**, **Comfortable / 舒适**, and **Large / 大字**. Default to Comfortable.
Expose the setting from a clearly labeled display/settings control available during planning and
battle. Persist it as a browser preference without including it in exported campaign data.

All measurements below are CSS pixels on screen at 100% browser zoom. For Pixi, measure the
rendered result after camera transforms, not only the declared font size.

| Element                                   | Compact | Comfortable | Large |
| ----------------------------------------- | ------: | ----------: | ----: |

| Secondary information and labels          |   12 px |       14 px | 16 px |
| Campaign city labels in readable view     |   14 px |       16 px | 18 px |
| Minimum primary control height            |   32 px |       40 px | 44 px |
| Battlefield tile side in readable mode    |   48 px |       64 px | 80 px |
| Battlefield troop counts in readable mode |   12 px |       14 px | 16 px |

Ornamental atlas inscriptions are exempt. Values, help, status, unit identity, and actions needed
to play are not ornamental. Use relative CSS sizing backed by shared tokens; do not scale the
entire page with a CSS transform.

### Camera and layout behavior

- Fit the battle board to its own bounds instead of fitting the surrounding 1000 × 720 campaign
  atlas. Keep the logical grid and world coordinates unchanged.
- Collapse campaign economy details during battle; keep essential date, battle, save, and language
  controls visible or directly reachable.
- Provide **Fit battlefield / 适应战场**, **Readable tiles / 清晰格子**, and
  **Center selected unit / 居中所选部队**, plus existing zoom/pan controls.
- Enter each new battle in readable mode with a friendly unit visible. A complete 10-row board
  need not fit when readable tiles are large; panning is the intended solution.
- Fit battlefield is an overview. On small fitted cells, simplify nonessential unit detail rather
  than overlapping it. Keep allegiance, troop type, selection, and readable counts available; the
  inspector and roster always expose full localized identity.
- Centering a unit reveals its complete tile in the unobscured map area. Keep Fit reachable even
  after excessive panning. Provide recovery from a viewport resize that moves content out of view.
- Language changes and ordinary state updates do not reset the camera. A preset change keeps the
  selection visible. Returning to the campaign restores its previous camera.
- Use deterministic label placement or suppression to avoid campaign label collisions. Selected
  and hovered cities take priority. All city markers remain selectable, and all 24 cities remain
  available in the city index. Do not move scenario coordinates to fix text collisions.

## 8. M4 — Rival aggression, safeguards, and save compatibility

### Player-facing behavior

Add `rivalAggression`: `cautious`, `balanced`, or `aggressive`. Default to `balanced`.
Display **Cautious / 谨慎**, **Balanced / 均衡**, and **Aggressive / 激进** in new-campaign setup and
campaign settings. Explain in both languages that the choice changes how readily rivals start
wars, while resources and combat strength remain unchanged.

The setting applies to every non-player faction, including AI-versus-AI conflicts. It does not
change tactical intelligence, resource income, damage, recruitment costs, or player march rules.
Rename the ruler-selection UI label **Difficulty** to **Starting position / 开局条件**; this does
not require renaming the existing static content field.

### Exact initial policy

Retain the existing attack heuristic, replacing only its multiplier with the preset value:

```text
attackingPower = sum(attackingOfficer.troops × (0.6 + attackingOfficer.force / 100))
defendingTroops = defending city reserves + all serving defending officers' troops
attackThreshold = defendingTroops × multiplier + cityDefense × 7 + 300
attack is considered only when attackingPower > attackThreshold
```

| Preset     | Initial multiplier |
| ---------- | -----------------: |
| Cautious   |               1.60 |
| Balanced   |               1.35 |
| Aggressive |               1.10 |

These are heuristic weights, not probabilities of victory. Keep strict `>` behavior, stable
faction/city/officer/target ordering, the 10-commander limit, no opening-turn AI attacks, alliance
checks, and ordinary command validation. Do not add random attack chances.

### Common safeguards

Apply these checks equally to every preset:

1. During AI mustering, available reserve is `max(0, city.reserve - 500)`. Do not create soldiers or
   remove already assigned soldiers merely to achieve a 500-reserve floor.
2. An AI march requires at least 500 reserves remaining at its source.
3. After the ordinary march food cost, require enough food for one current source-city upkeep:

   ```text
   marchFood = ceil(attackingTroops × 0.65) + 200
   sourceTroops = city.reserve + all serving officers' troops in that city
   requiredFoodRemaining = ceil(sourceTroops × 0.12)
   require city.food - marchFood >= requiredFoodRemaining
   ```

   Conservatively count the departing troops because they may return after defeat. Do not assume
   a victory, incoming harvest, or successful food purchase to pass this check.

4. On failure, skip that attack and continue existing domestic planning. Do not grant resources,
   silently shrink the army, or introduce transport planning.

These are departure safeguards. Subsequent combat or events may still cause shortages. Balanced
retains the old threshold but does not promise identical future campaigns because the common
safeguards intentionally change behavior. Keep the existing domestic priority algorithm, including
its current one-preferred-action limitation; investigate broader improvements separately.

### Command and persistence semantics

- Set the new-game value before its first autosave; retain default-compatible creation APIs.
- Change an existing campaign only through a validated command in `planning`, with
  `resolution === null` and no active battle. Reject in battle or finished campaigns.
- A successful change uses the existing autosave path. It changes the setting and normal revision
  bookkeeping, but not RNG, resources, armies, player command statistics, or committed orders.
- The value is effective at the next End Month. Loading or changing it must never replay AI plans
  or rewrite an existing queue.
- Keep `baye.save`, envelope version 1, `baye-atlas-1`, IndexedDB `baye-atlas`, its version, slot
  names, and existing import/export routes.
- Extend the schema additively. Missing aggression in an old save defaults to Balanced. An
  explicitly unknown or invalid value is rejected, rather than silently normalized.
- Preserve every old battle field, RNG, queue, cursor, orders, resource, and identity during load.
  New metadata defaults are allowed; rebuilding an old battle is not.
- Compatibility means old saves load in the new build. Do not promise that an old build preserves
  new fields when opening and rewriting a new save.

| A7  | Paired uninterrupted and save/reload runs remain deeply equal for identical seeds, presets, and command sequences. Include multiple battles within one month.                                                |
| A8  | All M0 legacy fixtures load. Their gameplay fields remain unchanged at normalization, and existing monthly resolution resumes without rerunning AI.                                                          |
| A9  | UI explanation and Starting position label are correct in both languages; changing visual preferences cannot change aggression.                                                                              |

### Simulation and tuning measurements

Correctness matrix: six playable factions × three presets × seeds `190` and `641` = **36 runs**.
Advance 12 months or until the campaign ends. Use End Month and auto-resolve every player battle.
Validate after each accepted command and at battle interruptions. Use bounded resolution guards;
nontermination must fail rather than being silently truncated.

Balance diagnostic matrix: six playable factions × three presets × seeds `1001` through `1010`
= **180 runs**, up to 24 months or campaign end. Use the same passive player policy and save the
raw per-run results. Run the baseline build with the same factions/seeds/policy for comparison.

| Metric              | Definition                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Attack rate         | Successful AI march orders per 100 rival faction-months; count a faction as active when it owns a city at monthly planning. |
| First war           | Turn of first successful AI march order; report runs with no attack separately instead of assigning them zero.              |
| Battle outcome      | Captures and defender holds, separated from committed orders that later stand down.                                         |
| Eliminations        | Rival factions eliminated by months 6, 12, and 24, with the count of runs still observed at each checkpoint.                |
| Provision shortages | AI city-upkeep executions that trigger shortage, per 100 AI-owned city-upkeep executions.                                   |
| Safeguard blocks    | Candidate attacks blocked by reserves or food; report each reason and overlap.                                              |
| Frozen willingness  | Acceptance rate for the same collected candidate snapshots under all three multipliers.                                     |

Do not extrapolate ended campaigns to later months. Report survival/early-ending counts so a
shorter campaign does not masquerade as a quieter full-length campaign. Instrument diagnostics
without consuming simulation RNG or changing gameplay counters.

**Hard gate:** zero invalid states, unbounded resolutions, or save-continuation mismatches in the
correctness matrix.

**Tuning review triggers:**

- Adjacent presets differ by less than 10% in normalized first-year attack rate. Report absolute
  rates as well; if a denominator is zero, describe the difference directly rather than dividing
  by zero. If all presets are inactive, investigate it.
- More than 10% of AI city-upkeep executions suffer provision shortages.
- More than half the initially active rival factions disappear by month 6 under Balanced in the
  observed runs.

These triggers require investigation and a written decision, not automatic claims of a bug or
ideal balance. More aggressive play need not produce more total wars in every complete campaign:
early conquests change future opportunities. Tune only the three multipliers first, retain common
safeguards, rerun the same matrix, and document final values. If this cannot resolve a concern
within scope, record the concern rather than silently redesigning the AI.

## 9. M5 — Persistent monthly rival report

### Content and presentation

Add a nonblocking **Monthly report / 月度军报**, available after monthly resolution finishes.
Show up to five highlights; allow expansion to the full retained report. Keep the Chronicle as the
existing detailed text history. Do not force a modal every month.

Record only committed, structured outcomes:

- Battle results: order ID, source/target city IDs, attacker, previous defender, outcome, and days.
- Alliance expirations: the two faction IDs.
- Border recruitment: successful rival recruit actions in cities adjacent to player territory at
  the time of recruitment, aggregated by city and faction with actual recruited counts.

Report recruitment as recruitment, not evidence of a planned invasion. Report a battle as a
capture only when ownership actually changed. A march that later stands down is not a battle win.

Highlight priority is deterministic:

1. Battles involving the player.
2. Rival captures bordering player territory.
3. Player alliance expirations.
4. Other rival captures.
5. Border recruitment.

Preserve event order for ties. Remaining retained events, including other defended-city outcomes
and rival alliance expirations, appear in the expanded report. Determine whether a capture borders
the player from ownership at the capture event and persist that classification; do not rewrite
the historical highlight priority after a later ownership change.

If fewer than five meaningful events exist, show fewer. If no qualifying events exist, show a
localized calm empty state. Selecting a city-related entry selects and centers that city without
issuing a game command; faction-only entries need not pretend to have a city target.

### Data contract and lifecycle

Maintain `reports: { pending, latest }`, each null or a bounded report. A report includes the
resolved month's turn/year/month, partial-history flag, structured events, and omitted-event count.
Label it with the month whose orders resolved, rather than accidentally labeling it as the new
planning month.

1. Start pending accumulation at End Month before AI planning.
2. Record recruitment only after the recruit action succeeds, using the actual result.
3. Record each battle once in aftermath, deduplicated by order ID. Capture previous ownership
   before mutation and compute capture status from the committed outcome.
4. Record alliance expiry in the existing expiry path, attached to the month being resolved.
5. Preserve pending data across interrupted battles, autosaves, manual saves, imports, and reloads.
6. Publish to latest and clear pending after resolution/upkeep completes. If an existing ending
   path terminates resolution earlier, finalize the accumulated report without additional upkeep.
7. Keep only the latest completed report and current pending report. Do not add an unbounded
   archive or event-sourcing system.

Use stable IDs and numbers; localize on display. Do not parse English Chronicle strings, which can
also be truncated by the existing log cap. Report bookkeeping must not consume RNG or the existing
gameplay `nextId` counter. Use local deterministic event ordering and order IDs for deduplication.

Limit each report to 128 events. Aggregate recruitment before truncation. If the limit is reached,
retain higher-priority events using stable tie-breaking and report how many records were omitted.
Do not claim a complete report after silently dropping events. Validate enum values, references,
numeric bounds, collection bounds, turn/date consistency, and duplicate keys on import.

Old saves missing reports default to null pending/latest. When continuing an old midbattle save,
lazily start a partial report for the already resolving month. Show only subsequently observed
events and label the missing earlier history. Do not reconstruct events from text or replay AI.
