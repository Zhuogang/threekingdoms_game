## 1. Assessment and scope

Finish v0.2 as a measured release candidate before expanding gameplay. The architecture and feature set are already substantial; the remaining work is measurement correctness, targeted balance changes, presentation, rendering efficiency, and human validation.

The current flow is React/Pixi controls → `session.execute` → simulation dispatch → validated cloned state → autosave and subscribers. Failed commands retain the original state. Rendering and localization are presentation concerns, not game commands.

Already implemented:

- Two scenarios, 24 cities, six playable houses per scenario, and the original 52 officers plus Guandu's Ma Chao.
- Campaign economy, diplomacy, prisoners, logistics, events, traits, difficulty presets, fog, and Hegemon victory.
- Tactical counters, morale, supply, terrain, walls, flanking, officer capture, and multiple tactics.
- Deterministic simulation, atomic command rejection, saved battle continuation, and v1-to-v2 migration.
- English/Chinese presentation and local portrait assets.
- Wave A measurement and tooling: battle observers, force-ratio buckets, tuning overrides, turtle-bot mode, frame-rate harnesses, and scenario-aware presentation accessors.

Do not assign these completed features again. Production rival AI already transports troops and coordinates attacks; T2 primarily improves the diagnostic player bot.

## 3. T0 — Correct measurement before tuning

**Owner:** Agent A. **Dependency:** none. **Type:** diagnostic correctness; no rule change.

**Files:** [botDiagnostics.ts](../../../tools/botDiagnostics.ts), [ai-diagnostics.mjs](../../../tools/ai-diagnostics.mjs), relevant diagnostic tests; a new `tools/tuning-sweep.mjs` can be introduced for T1.

Source findings:

- Any finished player victory currently sets `unified`, so a future Hegemon win would be mislabeled as unification.
- The older contested summary uses attacker/defender ratio 0.6–1.6 inclusive, while the newer buckets use a symmetric maximum/minimum ratio below 1.6.
- Current survival counts some early rival victories as survival because the player retains cities. That is a documented definition, but it differs from remaining active at the measurement horizon.
- The wrapper builds a shared `bot-runner.mjs`, and battle details use a shared output filename. Parallel sweeps can overwrite each other's artifacts.

Implementation steps:

1. Record true total-map unification, Hegemon victory, player elimination, rival victory, and unfinished campaigns separately. Include winner, ending reason and ending month. Do not infer rival unification from `winner` alone: player elimination can name the largest rival without that rival owning the entire map.
2. Use one symmetric contested-battle definition and explicit boundary rules everywhere. Include attack, tactic and move-only shares in each force-ratio bucket.
3. Record actual month-48 and month-96 city counts with explicit early-terminal handling. Do not substitute final territory for both checkpoints.
4. Retain the historical survival metric for comparison while adding active-at-horizon and terminal-outcome counts.
5. Record revision, scenario, house, seed, bot policy/version, tuning values, horizon, sample counts, numerators/denominators and elapsed time. Reject non-finite or out-of-range numeric overrides.
6. Run sweeps sequentially initially; isolate runner and battle-detail paths before enabling parallel jobs.
7. Add focused tests for Hegemon versus unification versus elimination, force-ratio boundaries, and observer/replay equivalence.

**Acceptance:** corrected baseline reports are reproducible; outcomes and cohorts are unambiguous; focused tests pass; observer replay produces identical state; legacy hashes remain unchanged.

**Handoff:** metric definitions, baseline artifacts, tests run, and the exact configuration for T1.

## 4. T1 — Tune battles through controlled experiments

**Owner:** Agent A. **Dependency:** T0. **Type:** experiments first, then intentional rule changes.

**Files:** [battle.ts](../../../src/game/battle.ts), [aiPolicy.ts](../../../src/game/aiPolicy.ts), diagnostic tools, new `tools/tuning-sweep.mjs`, [battle-rules.test.ts](../../../tests/battle-rules.test.ts), related battle tests, [rules](v0.2-rules.md) and [notes](v0.2-notes.md).

1. Establish a corrected baseline: both scenarios, six houses each, seeds 2001–2003, Standard difficulty, Balanced rivals, 48 months: 36 campaigns.
2. Freeze player-bot behavior during the sweep so comparisons isolate battle and strategic-AI levers.
3. Use `DIAGNOSTIC_TUNING` for one-lever experiments. Produce a table of every target and guardrail under `.artifacts/tuning/`.

| Lever                       | Initial experiment values                         | Main question                                                |
| --------------------------- | ------------------------------------------------- | ------------------------------------------------------------ |
| Hold-near-camp radius       | 2, 3, 4                                           | Does defensive positioning produce excessive waiting?        |
| Balanced attack multiplier  | 1.35, 1.2, 1.1                                    | Are strategic attacks too consistently overwhelming?         |
| Normal damage rate          | 0.25, 0.21, 0.18, 0.15                            | Can engagements last longer without stalemates?              |
| Fire/Rockfall damage        | Scale proportionally with normal damage initially | Does the tactic balance remain coherent?                     |
| Counter/guard-counter rates | 0.5/0.7, 0.6/0.8, 0.7/0.9                         | Do victories become more costly without excessive reversals? |

The latest waiting breakdown makes positioning the first investigation: much move-only activity comes from units held near camp or unable to reach enemies. Treat the proposed values as experiments, not preselected defaults.

4. Select a small number of promising combinations. Compare overall and contested results, contact timing, ending reasons and waiting reasons.
5. Reject combinations that fail guardrails. Confirm finalists at 96 months and on additional seeds not used to select values.
6. Apply the chosen defaults. Explain their measured effects and update rules and notes.
7. Review and regenerate legacy continuation hashes only for intentional rule changes, then verify without regeneration.

### Targets and guardrails

| Measure                                     | Acceptance                                               |
| ------------------------------------------- | -------------------------------------------------------- |
| Median battle duration                      | 5–12 days                                                |
| Close battles: winner retains < 50%         | ≥ 30%                                                    |
| Attack / tactic / move-only shares          | No category > 60%                                        |
| Day-limit endings                           | < 10%                                                    |
| Camp captured by day 3                      | < 10%                                                    |
| Contested upsets                            | 15–30%                                                   |
| Supply exhaustion                           | 5–20%                                                    |
| Raids producing battles                     | 40–80%                                                   |
| Approachable/Balanced survival at 48 months | ≥ 80%                                                    |
| Auto-resolve p95                            | < 50 ms                                                  |
| Mirrored v2-versus-v1 battle checks         | Existing strength, decisiveness and duration checks pass |

Keep instant camp capture. If contested battles end too often by camp capture, investigate defending and approach behavior. Do not make the AI ignore an immediately available victory to inflate battle duration.

The archived proposal to break only after a full day routed is not an existing numeric lever. The current `armyBreak` knob is boolean. Delayed breaking would need saved state, validation/migration and separate tests; defer it unless simpler experiments fail.

**D8 decision point:** use contested-only acceptance only if that cohort actually meets all three targets. Preserve overall metrics alongside it. Otherwise present the misses explicitly for a design decision; do not silently lower thresholds.

**Acceptance:** selected configuration and causal explanation; reproducible comparison evidence; all guardrails preserved; three targets met or D8 explicitly recorded; rule tests and intentional continuation-hash updates validated.

**Handoff:** full sweep table, finalist/held-out evidence, changed constants, rule documentation and D8 disposition.

## 7. T7 — Improve rendering efficiency and measurement

**Owner:** Agent B. **Dependency:** can start alongside T0/T1; serialize with T4. **Type:** presentation/performance only.

**Files:** [GameMap.tsx](../../../src/rendering/GameMap.tsx), [FPS tests](../../../tests/fps/fps.spec.ts), [FPS configuration](../../../playwright.fps.config.ts), relevant camera/presentation/browser tests.

Current facts: DPR is already capped at 2. The ticker renders continuously; foreground redraws destroy and rebuild objects. The current FPS fixture is seven versus ten, and browser animation-callback cadence alone does not prove that Pixi is producing correct updated frames.

1. Improve instrumentation before optimizing. Distinguish browser frame cadence, actual render work and visible response to interaction.
2. Build a validated 10-versus-10 fixture with the threat overlay. Exercise movement, attack feedback and campaign panning, not just a static battle.
3. Render on invalidation: state, selection, pan/zoom/reset/focus, resize, locale, display preset, overlays and reduced-motion changes. Coalesce repeated invalidations.
4. Continue rendering during movement tweens and casualty effects, including their final frame. Preserve a visible selected-unit indicator without requiring a perpetual expensive full-scene pulse.
5. Separate terrain/background work from units and overlays. Reuse stable graphics/text; bound caches and clean them up on scenario, battle, locale and app lifecycle changes.
6. Benchmark lower/configurable resolution against the existing DPR cap of 2. Retain readable text and labels; do not lower resolution without evidence.
7. Check interaction after idle, rapid commands, resize, language changes, battle entry/exit and reduced motion. Look for stale canvases, missed final frames, ghost nodes and leaks.
8. After T4 is integrated, run baseline, 4× CPU, 6× CPU and SwiftShader measurements serially. Record browser, hardware, viewport, DPR, median intervals and slow-frame share.
9. Arrange one real low-end/integrated-GPU run on the release candidate and record the actual observations.

**Acceptance:**

- Baseline and 4× CPU active interaction meet median frame interval ≤ 33.33 ms, with fewer than 10% intervals above approximately 38.33 ms.
- Idle work falls while interaction still produces immediate correct visuals. A fast callback loop with a stale canvas is not a pass.
- Aim for ≥ 30 fps under SwiftShader where attainable; report the real result and any remaining limitation. CPU 6× and software graphics are distinct from the enforced baseline/4× checks.
- The release checklist's real low-end-machine result is recorded independently. CPU throttling and software graphics do not replace it.
- Simulation behavior and existing legacy hashes remain unchanged.

**Handoff:** before/after performance artifacts, correctness evidence, environment details and outstanding hardware checks.

Update current README, summary, next-steps, rules, notes, credits and playtest record as applicable; preserve archived documents as history. Each result must identify the tested revision, configuration and environment.

Known documentation drift to resolve during final integration:

- An implementation-guide paragraph says save payload version 1, while the encoder writes version 2.
- The guide's alliance-odds formula omits current policy, shared-threat, strongest-faction and reputation modifiers.
- Verification counts describe different revisions and must not be presented as one fresh run.
- Summary/notes say the branch is not pushed. At review time HEAD matched the local remote-tracking reference, but no fetch verified the live remote. Check actual state before making a release claim.
- Portrait counts, theme wording, difficulty descriptions and performance-fixture claims need to reflect the final implementation.

Record final metrics, sample definitions, configuration, limitations, D8/D9 outcomes and the manual hardware result in `v0.2-notes.md`. Keep an issue ledger mapping every task to evidence or explicit deferral.

### Release action

On later authorization to implement/release, push the intended branch and open the PR to `main` when the gates are met. Inspect CI on the PR revision and resolve failures before declaring it ready. Saving this plan authorizes no push, PR, merge or deployment.

**Acceptance:** all applicable release gates satisfied or explicitly deferred where the checklist permits; final evidence matches the candidate; human findings handled; PR has green CI on the tested revision when release is authorized.

**Handoff:** final checklist, command results, diagnostic artifacts, human evidence, decisions, limitations and PR status.

## 13. Required agent completion report

Every implementation handoff must include:

- Task IDs, owned files and dependencies consumed.

- Acceptance criteria, with pass/fail/pending evidence for each.
- Exact checks run, tested revision, configuration and artifact locations.
