**实施后复核完成：** 先复现后修复整编抵达／看押／迁都、微量断粮、日末击溃、俘虏粮债、失城后等待改道、中立看押供粮及日快照势力关联，共新增 10 个回归用例。全量 465 项通过；本轮重点覆盖的中英伤兵、俘虏、撤退及多战场推进 12 项浏览器回归通过。没有调整设计数值或增加子系统。

## 一 实施范围与规则基准

实现保持单将单基础兵种，可战兵加随将伤兵共同占用 10000 人容量。新出征自动将旧伤兵留城，保留来源与经验；只剩伤兵可返程，不能新出征。不增加独立军团、军医、医院、伤情分级、单队撤离或追击操作。

| 规则             | 本轮实现默认值                                                                         |
| ---------------- | -------------------------------------------------------------------------------------- |
| 战斗减员转伤兵   | 60%，比例余数累计；非战斗减员不生成伤兵。                                              |
| 有退路时撤退判俘 | 未接战为 0；接战后有序撤退每将 5%；被迫溃退每将 25%。                                  |
| 无可用退路       | 明确预告整军投降；可达友城正在交战可城外等待，不算无路。                               |
| 逃脱携带人员     | 有序撤退保留全部随军生还者；被迫溃退保留全部可战兵和三分之二随军伤兵。                 |
| 自动恢复         | 每城按兵种汇总，日初合法休养伤兵的 10% 向上取整，再按来源分配。                        |
| 招降整编         | 10 个有效驻城日，期间不能作战、征调或提供可用留守兵力。                                |
| 人员维持         | 所部、预备兵、待归队人员、伤兵和俘虏都计口粮，骑兵两倍；可以合法释放或遣散以缩减负担。 |

将这些数值集中配置，测试引用同一规则入口。先按当前设计实现，不边接线边调整概率或恢复速度；测试须保留 5000 → 3000 等独立的规则期望，不能只引用实现常量再用同一个公式计算期望而漏掉错误配置；数值调整集中到 W7 的试玩反馈之后，并记录理由。

按此顺序串行推进，共享的 `types.ts`、`engine.ts`、`storage.ts` 每阶段只做该阶段必需的变更。每阶段可以拆为数个本地提交，但提交前应能通过对应类型检查和定向验证；不把类型、状态和存档拆成互不兼容的提交。

阶段编号是工作顺序，不强制一阶段一个提交。W2 与 W3 直接耦合：如果战场开始产生伤兵后，既有战役回归必须同时有新结算才能通过，就将二者作为同一组完整变更提交；不能靠跳过既有失败用例或允许伤兵被旧结算丢弃来制造阶段完成。

- **节点 A，完成 W2：** 伤兵与经验的规则可独立验证，尚不是可玩的完整战役功能。
- **节点 B，完成 W5：** 后端生命周期、存读档和 NPC 行为接通，可以进入完整界面验收。
- **节点 C，完成 W7：** 交付可本地试玩候选版，并分别列明自动化结果、实际试玩观察和仍未完成的人工验证。

## 三 W0 实现契约与基线

先把设计对应到实际状态结构，避免写到战后结算时才发现伤兵没有合法去处。W0 不改变玩法参数。

### 工作内容

1. 记录实际 HEAD、工作区改动、当前类型检查与相关兵力、战斗、存档测试结果。保留已有美术和其他无关文件，不将它们混入本功能提交。
2. 确定下节的人员来源、驻地、看押和可用兵力契约，特别是留城老兵与普通预备兵的关系。
3. 明确同一天的口粮责任、日初休养资格，以及在日游标创建前执行出征、撤退等命令时如何冻结这些信息。日初资格数据与推进游标分开持久化：不能提前创建 `DayResolution` 后误锁正常命令，也不能等 `advanceV03` 才临时把当前状态当日初。见下方每日协议。
4. 确定新增存档结构的识别标记、旧存档拒绝提示与原始数据保留方式；用明确的 schema 修订标记区分，不能依赖捕获任意字段报错来猜旧版本。当前外层为 `version: 3`、`ruleset: hegemony-3`，不因本功能擅自把整个游戏改称 v0.4；也不加入旧存档迁移。

### 必须固定的实现契约

| 对象             | 建议职责与约束                                                                                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 武将所部         | 延续 `troops` 表示健全兵人数的现有字段，并增加伤兵与所需整编状态。是否可用通过共享查询判断；不让 UI、AI 和订单各自推算。单将仍只有一个基础兵种。                                                            |
| 城市普通预备兵池 | 继续存放真正已经合并的普通兵源，按兵种维护人数与平均经验。                                                                                                                                                  |
| 留城人员记录     | 单独保留稳定记录 ID、可为空的来源武将、所属势力、驻地、兵种、健全人数、伤兵、经验与整编状态。同一来源武将允许多条不同经验或整编进度的记录；禁止重复的是记录 ID 和实际人员归属。                             |
| 城市兵力汇总     | 各口径分别派生，不能用一个总数兼任兵源和战斗力。`reserve` 保持普通 `reservePools` 合计；`garrisonTroops` 只含实际可用驻城所部与无主将守军；留城来源通过共享查询计入可用兵源或后勤总人数，不能自动变成民兵。 |
| 临时战场编队     | 保存实际参战快照、成员对应、可战兵、新增伤兵、永久损失、比例余数和接战标记。进行中的战场人数不与武将上阵前快照重复相加。                                                                                    |
| 行程清单         | 区分己方随军人员与俘虏，人数作为清单汇总而非另一份兵池；纯伤兵返程合法。跨行程转移必须一次移出、一次加入。                                                                                                  |
| 俘虏位置         | 原势力与看押方分开；位置可为看押城市或押送行程，必须恰有一个实际位置。不能只用原有 `captured.cityId` 承担在途押送。                                                                                         |
| 日游标           | 冻结休养资格与供粮责任，保存治疗、整编、归队和供粮步骤的完成状态；拆分与转移继承当日已处理信息。                                                                                                            |
| 报告             | 保存当场结果快照，不通过当前武将、兵池或城市的可变人数反算历史。                                                                                                                                            |

路线契约同时明确 `movingFactionId`（字段名可调整）：正常出征默认命令所属势力，撤离与获释归还显式传入移动方；失城或看押城市只获准作为离开起点，后续可通行城市按移动方计算。现有 `planRoute` 从 `source.factionId` 推断，`friendlyRefugeHop` 又按无通行过滤的道路距离找第一跳，二者不能直接当作新机制已经具备的退路能力。首选目的地按未交战、原出发城及 ETA 顺序统一比较，预览与执行共用查询。

上述名称可在编码时调整，职责不能省略。尤其不能先把所有留城伤兵并入城市平均经验，再试图从汇总数恢复原将的精锐。

### 每日协议与计数边界

- 日资格快照在新局和每个战略日开始时存在，记录日初位置、所属、伤兵数与粮食条件。当天新到或新招降者从下一完整驻城日开始恢复或整编；离城、换归属或进入战斗后失去当日资格。同城拆分、归还只继承资格，不能重新生成。
- 每条实际人员记录保留当日已供粮信息；派生汇总不单独缴粮。战斗按日收费或结束时补收一次，随后回城或新建返程不再收本日城市／行军费；行军到达当天由原行程供粮，等待也按行军计粮。拆分、转移和合并必须保留相应人数的处理状态，不能把半数已付粮的一池人简单标成全部已付。
- 治疗与整编在统一日收尾、月结之前各执行一次，再尝试合法归队；恢复出来的人最早参加之后新建的战斗。日初资格快照、日中人数变化与当前记录必须相互核对，禁止把已阵亡或散编人员按旧快照恢复。
- 月结城市兵日保留已经发生的责任，出征、归还、遣散不能抹掉旧账。原有失城重置旧主兵日的规则不顺便改为向新主追债；核对报告与留城军粮结算，不能同时收旧账和再次收同批战斗粮。

### 验收

- [x] 一名士兵在城池、战场、行程和看押账目之间只有一个实际归属；人员总数、永久损失和遣散人口可以核对。
- [x] 每日快照覆盖命令发生在 `advanceV03` 之前的情况，而不只覆盖已经存在的日游标。
- [x] 确定来源记录及汇总的唯一写入入口，没有两个可独立修改的兵力总账。

## 四 W1 兵源记录与存档基础

主要位置：[共享类型](../../src/v03/types.ts)、[人员与来源工具](../../src/v03/campaign/personnel.ts)、[普通兵池工具](../../src/v03/campaign/troop-experience.ts)、[初始状态](../../src/v03/initial-state.ts)、[存档](../../src/v03/platform/storage.ts)。

### 工作内容

1. 落实 W0 的所部、留城记录、看押位置与日状态字段，新局全部初始化为合法的零伤兵、零整编状态。
2. 扩展人数与经验的合并、拆分和损耗工具；经验仅在该记录所有人员均为空时清零。W1 新增 `campaign/personnel.ts` 处理含伤兵记录，普通健全兵池继续沿用原工具；战斗与月结调用方在 W2／W4 迁移。自动存放保留来源，实际配兵合并才加权。可用人员与不同整编剩余日的人员不能为了平均经验而压成一条记录；不按人数创建士兵实体，不为治疗另设批次。
3. 提供统一查询：总人数、可用战斗人数、同兵种可分配兵源、随军人数、骑兵计粮人数和合法归队容量。新查询先保持零伤兵状态下的原行为。
4. 同步更新严格 schema、关联校验、新局 fixture 和存档往返。识别旧结构并友好拒绝；拒绝导入时不覆盖原始文件或自动存档，也不依靠解码成功才能保存旧存档原文。
5. 核对存档压缩策略，不能把仍有伤兵、待归队人员、俘虏或未完成行程的来源记录当作历史清理掉。

### 验收

- [x] 零伤兵新局仍可征兵、配兵、出征和保存；新字段不会改变已有兵种、等级或人数。
- [x] 只有伤兵的记录能保留经验，拆分合并不增加总人数、经验总量或可用兵力。
- [x] 错兵种、超一万人、重复记录 ID、无看押位置和错误汇总均能被校验拦住；合法来源记录存读档不丢精度。

定向验证以现有[兵池测试](../../tests/v03/campaign/troop-experience.test.ts)和[存档测试](../../tests/v03/platform/storage.test.ts)为基础，新增来源记录与可用兵力测试。此阶段不接入战斗生成伤兵。除固定算例，增加有固定种子的拆分、治疗、损耗和实际合并序列，校验人数、容量、记录唯一归属及加权经验总量；不要求数学上逐位相等的浮点累计，明确小容差。

## 五 W2 战斗伤兵与经验

主要位置：[战场类型](../../src/v03/battle/types.ts)、[战斗引擎](../../src/v03/battle/engine.ts)、[战斗经验](../../src/v03/battle/experience.ts)，以及战役编队生成入口。

### 工作内容

1. 普攻、反击、火计、伏兵和落石统一使用有效战斗减员分配器；伤兵占 60%，余数累计，不能因分多次攻击而改变结果。
2. 记录已接战状态：任一方发起普通攻击或敌对计策即永久标记本场已接战；支持计策或单纯移动不误标。
3. 生成攻守编队前将旧伤兵留城；本场伤兵不能被再次攻击、占格、反击、占营或战中恢复。伤害预览仍表示失去战斗力的人数，明确它不等于全数战死。
4. 一方全军可战归零仍然结束战斗，单个单位归零只退出战场；士气低于 20 仍单独处理。预览、命令和 AI 共用结束原因判断，已满足击溃或士气溃败条件时，撤退命令不能覆盖为较低风险原因。
5. 经验只奖励实际参战生还者与本场新伤兵，排除战前伤员；同编队各成员保留原经验，并按原人数比例分回损失和伤兵。可战、伤兵、永久损失使用同一次有上限的整数分配，逐成员三者之和必须等于开战人数；不能把三列各自独立四舍五入后造兵或让某成员超额。
6. 移除 `openBattle` 的“至少 500 民兵”保底；仅有真实民兵才建该编队。无可战守军时立即记录并结算结果，不向玩家打开空战场。实际战术构造器允许空 roster，新增存档规则允许只有进攻单位的已结束记录，不虚构守军；零战斗不发伤害或参战经验。
7. 将整军撤退命令改成明确己方 side 的军队级动作，不再必需存活 `unitId`；后端校验操作方与战果。为 W3／W5 提供相同入口，W6 再完成玩家界面。

### 验收

- [x] 5000 人累计有效战斗减员后为可战 0、伤兵 3000、永久损失 2000，经验保留；超额伤害不能重复生成伤兵。
- [x] 小额多次伤害与一次等额伤害的总伤兵一致；断粮减员没有转伤兵或参战奖励。
- [x] 保留既有反击、水战和计策倍率；战前伤兵不刷经验、仅有新伤兵的参战者不丢奖励。

定向验证扩展现有[战斗测试](../../tests/v03/battle.test.ts)、[经验测试](../../tests/v03/battle-experience.test.ts)和[兵力流转测试](../../tests/v03/campaign/troop-flow.integration.test.ts)。此节点只证明伤兵战斗规则，完整去向由 W3 接通。

## 六 W3 战后去向与真实行程

主要位置：[战役引擎](../../src/v03/engine.ts)的 `allocateSurvivors`、`finishBattle`、`handleArrivals`，[路线与行程](../../src/v03/calendar/index.ts)，以及[出征服务](../../src/v03/governance/services.ts)。建议将退路与战后分配计算提取为纯函数，避免继续扩大 `finishBattle`。

### 工作内容

1. 生成战后分配方案：先冻结参战成员与原归属，计算退路、结束原因、每将风险和人员去向，再一次应用。纯计算接收 RNG 状态并返回决定与下一状态，只有实际成功应用时才一并提交；有 `resolved` 保护，取消或预览不消费随机数。先安排全部人员与城市归属，再做继位和势力覆灭，避免处理中途暂时没有自由将领而误灭势力。
2. 接通攻守同规则的 0%、5%、25% 判俘；每将固定顺序抽一次并保存结果。守方失城不自动全俘，临时编队成员不连坐。
3. 创建攻方返程、守方退往友城、纯伤兵返程、独将逃脱和胜方押送。路线使用 W0 的移动方身份与实际 ETA，不依赖新城主。统一所有入城分支：可达友城交战时可城外等待，`waiting` 和普通友城卸货分支都不能绕过这项检查；改道不重新判俘。
4. 有序撤退不损伤兵；被迫逃脱按三分之二保留伤兵，其余计永久失散；被俘者不再扣一次伤兵。
5. 先结清本日尚未收取的战斗口粮，再分配余粮：胜方自有粮按驻留或返程处理，败方余粮在返程与被俘人员之间分配。去除既有“全部余粮先归胜方”的重叠路径；城市库存超上限时显式记溢出损失，守恒式包含该项。供粮基础与 W4 共用，手动结束不能漏账。无可战守军的直接结算不收虚构战斗口粮，攻方抵达日仍属行军账，城内人员仍属城市账。
6. 按征服、占领劫掠、突袭和平局分别结算城市；留城旧伤兵不跟随远方将军被俘。失城结算覆盖原势力未参战自由武将，去重后按同一风险表处理，旧伤兵和整编库存按留城规则处理；无守军直接结算沿用未接战规则。战后报告使用本次分配快照。
7. 开战分粮按设计的前线战斗预算、后方粮耗预算自动划拨，删除 `target.food = 0` 的全量搬运逻辑；W4 的恢复与城内供粮必须建立在实际留存库存上。城市全部库存不能同时作为可用城库和战场粮。

## 七 W4 日恢复 整编 口粮与配兵

主要位置：[每日游标](../../src/v03/calendar/day-resolution.ts)、[日历与补给](../../src/v03/calendar/index.ts)、战役每日与月结流程、[城市行动](../../src/v03/governance/city-actions.ts)、[库存权限](../../src/v03/governance/authority.ts)、[订单](../../src/v03/governance/orders.ts)。建议拆成恢复、粮账、配兵三个可审阅提交，均依赖 W1 的共享查询。

### 工作内容

1. 在现有日流程中接入日初资格快照与一次性执行标记，按兵种汇总每日 10% 治疗，再稳定分配到原记录。当天新抵达、被释放到行程、已换归属或失守后散编的人员不被重复治疗或复活。
2. 在合法驻城日推进整编；在途或无粮日暂停。处理同城自动归队，校验原将健在、同势力、未被承诺占用、已完成整编且有容量；留城老兵不跨城传送。

6. 核对月事件回写与所有经验清零路径，不因可战归零清掉尚存伤兵，也不把新模型压回旧版月度摘要而丢失来源。

## 八 W5 俘虏 城市与 NPC

主要位置：[俘虏系统](../../src/v03/campaign/prisoners.ts)、战役城市易主和继位处理、[自治](../../src/v03/governance/autonomy.ts)、[NPC 出征回归](../../tests/v03/engine.rival-dispatch.test.ts)。

### 工作内容

1. 招降同步移交随俘所部，启动 10 日整编；未归其看押的后方留城人员不随将改投。招降失败不改变部队归属。

## 十 W7 全流程验证与试玩

### 自动化主场景

用固定种子与明确人数设置建立可复现的完整命令链，断言实际结果和存档合法性：

| 场景                         | 必须核对的结果                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 5000 精骑被击溃，友军胜利    | 3000 伤兵保留经验；回城恢复、再次出征留后方、合法归队；不是全灭或立即满编。    |
| 占领战守方主动撤退           | 失城但按将概率处理；逃脱者真实行军，被俘者及所部合法看押，城内旧兵源另行清算。 |
| 同编队多人部分逃脱           | 不连坐、不重复抽签；可战、伤兵、永久失散、俘虏与余粮守恒。                     |
| 友城交战或返程目标易手       | 等待或改道，不凭空全俘、不自动增援，不重算原战果。                             |
| 招降 3000 老兵               | 供粮、恢复与 10 日整编正确；整编前无可用兵力，之后保持兵种和经验。             |
| 无路返乡的俘虏               | 可明确释放并遣散，结束军事供粮；不能既增加人口又保留部队。                     |
| 小部队带大量旧伤兵的经验场景 | 只有实际参战者及本场新伤兵获奖，后方经验不被刷高或静默稀释。                   |
| 多战场与月界续算             | 治疗、整编、归队、口粮、判俘、报告和人口回流均只执行一次。                     |

补充四组边界链路：无守军占城及城内零兵武将去向；开战留粮且后方恢复；招降失败后同月释放与两边交换月锁；NPC／托管主动撤退。再覆盖多人合编的 1、2、3 人整数分配、同来源不同经验记录、城市人口与粮食上限，以及当日命令发生在日游标之前的保存续算。

### 实际试玩

保留三个短场景存档和操作记录：弱方败退后再战、优势方连续胜利并招降、多将有序撤退。至少回答：

1. 玩家知道该不该撤，也愿意在全军崩溃前撤吗；单将概率与整军实际损失是否符合预期？
2. 败方保存的精锐能形成下一次有效作战，还是返程和养伤使其长期无法使用？
3. 胜方是否能靠招降在几乎没有新增成本时持续扩大优势，10 日整编是否有实际作用？
4. 新预备兵粮耗是否造成新局或自治城市普遍断粮；玩家是否能看懂并使用遣散、释放来纠正负担？
5. 自动留伤兵和归队是否减少操作，且没有意外补兵、经验稀释或抢占订单兵源？

这些试玩由实际执行者记录；未执行时保留为未完成，不用自动化断言替代玩家感受。需要调整数值时，优先修改统一参数、复测受影响场景，不继续增加医疗或俘虏子系统。
