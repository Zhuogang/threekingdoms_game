## 2. 需要替换的现有假设

基线为 `ea29af2`，主要代码在 `src/game/battle.ts`：

- `createBattle` 写死 12×10；`DEPLOY_ROWS`、营地行、河道和 `WALL_COLUMN` 使用旧图固定位置。
- `stepCost` 仅允许 `naval` 进入水格，其他兵种返回不可达；水军进入水格只花 1 点。
- `terrainDefense` 为水上 `naval` 提供 0.82 的承伤系数，即原来下水会更耐打。
- `fireDamage` 对水上目标使用 0.35 的独立伤害系数。
- `rockfallDamage` 当前未接收战场对象，无法读取目标是否在水上。
- 城市防御值会触发城墙生成，驻军单位也读取城市防御值；必须逐项审查这些关联。
- `campaign.ts` 的语义校验明确要求 12×10，基础存档 schema 的范围宽松不代表已经支持新图。

以上限制均不应为了旧版兼容保留在 v0.3 分支的有效规则中。保留旧文件历史记录，不需要删除历史文档或测试证据。

## 3. 地图与部署

### 3.1 逻辑地图合同

建议在集成轨道统一状态定义后，由本轨道实现以下地图数据：

| 字段                                        | 约定                                                                                 |
| ------------------------------------------- | ------------------------------------------------------------------------------------ |
| `mapId` / `templateVersion`                 | 稳定样板 ID 与配置版本；生成后随战斗保存                                             |
| `width` / `height`                          | 固定 24 / 20                                                                         |
| `regionId`                                  | 地理轨道提供的地域标识；不依赖画面色板名称                                           |
| `approachDirection`                         | 进攻路线最后一段的方向，来源于战略路线；使用明确的方向枚举                           |
| `terrain`                                   | 行优先 480 格；建议 `plain / forest / hill / water / cliff` 五类，不再包含 wall/gate |
| `attackerDeployment` / `defenderDeployment` | 可用部署格列表，彼此不重叠，每方至少容纳 10 单位                                     |
| `objectives`                                | 双方野战营地等战术目标的坐标与归属，独立于地形枚举                                   |
| `landmarks`                                 | 渡口、道路、坡口等有语义的地标；如仅是绘画，标为装饰，不生成隐藏规则                 |
| `seed`                                      | 可复现的地图种子；存储生成后的地形，不在读档时重新生成                               |

`cliff` 是明确不可通行的陆地峭壁，不能画成可走坡地；不是“只有部分兵种才能进入”的新特权地形。所有 `water` 格都必须对所有作战单位可进入。不可玩的海面和远景河面放在地图边界之外，不用水军技能、深水等级或暗藏阻挡来限制水格。

**战术下水不等于战略地图可横渡任意海域。** 城际交通仍按批准的道路/水运路线计算；战术水格表示本场战斗可通行的河道、湖湾或浅岸作战区域，运输方式作抽象处理。

### 3.2 部署与接敌距离

- 地图长宽翻倍，但不把两军简单挪到距离最远的两条边。
- 每方部署区至少提供两排空间，按地图中轴和进入方向产生；营地位于本方后方。
- 对等开放野战初始接敌距离目标为步兵正常推进约 2–4 个战斗日；渡河、山谷地图分别测量，不用同一个平均值掩盖等待。
- 主要地图应有侧翼或替代通路；关隘样板可以狭窄，但仍要保证所有初始单位有合法位置及可达出口。
- 开局单位不得放在峭壁、对方控制格或相互重叠的格子；默认部署在陆地。单独的水面开局夹具用于规则测试，不要求第一版提供纯水面出生玩法。
- 营地由地图定义显式给出，不再从 `x=0/width-1, y=height/2` 推导。

### 3.3 四个首轮可玩样板

| 样板     | 地理与空间要求                                       | 核心战术验证                                     |
| -------- | ---------------------------------------------------- | ------------------------------------------------ |
| 汉中山谷 | 河谷、连续山脊、可走缓坡及少量峭壁；进入方向来自路线 | 选择谷底推进或坡口绕行；不能把整个盆地都当成高山 |
| 寿春河网 | 连续淮河区域水道、两岸展开区、至少两条实际过河选择   | 争夺岸边火力位；在渡口快速过河或在别处冒险下水   |
| 下邳平原 | 开阔接敌区、局部林地、田地道路和水线                 | 步兵稳线、骑兵迂回、弓兵射击；不能只剩直线抢营   |
| 成都平原 | 农田、疏林、灌溉水道与城郊开阔地                     | 平原上的走位与河岸选择；远景山体不变成全图峭壁   |

模板选择使用城市地域、路线方向和地图种子，不仅根据目的地选择一种色板。道路和田地若没有规则效果，应由 UI 明示其基础地形；不得暗示它们具有额外补给、治疗或速度加成。

### 3.4 无攻城的城市战斗

- 敌军抵达城市时，发生该城区域的野战；胜负后由战略层应用占领、突袭或撤退结果。
- 地图可显示远处城市作为不参与交互的背景地标，但本轨道不提供城墙、城门、耐久、登城或城内阶段数据。美术需求中也不包含攻城资产。
- 保留野战营地争夺、全歼/全军溃败、撤退和战斗期限等可用机制。营地是战术据点，不是需要攻破的城市建筑。
- 当前 `city.defense >= WALL_DEFENSE` 的地图分支应完全退出 v0.3；新状态 schema、公开规则与城市界面移除城墙防御字段，不保留未使用的攻城数值。
- 驻军/民兵统一采用基础武力 **40**，各城一致，作为可调的实现初值。正常兵力、士气、状态、兵种和实际地形因素继续作用，不继承原 `40 + floor(defense/10)` 的城防加成；本轮不另建准备度或训练系统作为替代依赖。
- 营地只作为野战目标覆盖层，站在营地上按其真实底层地形计算费用和伤害。删除旧 `fort → 0.65` 的承伤保护，不从帐篷、旗帜或目标身份获得额外防御倍率。可以保留营地占领胜负条件，但不能以营地之名留下隐形城墙。

## 4. 水上移动规则

### 4.1 统一上下水

建议基础规则为：**一次路径移动中，只要一条相邻格边的起点或终点是水格，这一步至少消耗 2 移动力；上岸到原本费用更高的陆地时取较高值。** 陆地到陆地仍按普通目标地形费用计算；峭壁不可进入。

| 一步移动       | 消耗                                   | 备注                                       |
| -------------- | -------------------------------------- | ------------------------------------------ |
| 陆地 → 水      | 2                                      | 立即进入水上状态；不另收登船费或整回合等待 |
| 水 → 水        | 2                                      | 对所有兵种一致                             |
| 水 → 普通陆地  | 2                                      | 立即退出水上状态                           |
| 水 → 林地/山坡 | `max(2, 该单位进入目标陆地的普通费用)` | 不让骑兵借水边绕过原本更高的陆地进入费用   |
| 任何格 → 峭壁  | 不可达                                 | 与兵种、技能无关                           |

护卫基础移动力为 2，因此可以一回合完成一次入水或一次上岸，不会被额外固定费用困死；并不表示它能在同一回合往返。进入水域不改变兵种 ID、不消耗船库存、不新增装备栏；所有兵种使用通用舟形/运输平台表达抽象运输，尤其不让骑兵看起来站在水面上。载具绘画不是解锁条件，也不代表一个可买卖的军队实体。

基础兵种移动力先保留当前值作为比较起点：步兵 3、骑兵 5、弓兵 3、水军标签单位 4、先锋 4、护卫 2。允许基础速度不同，但**不得给某兵种水格低价、免罚、独占通行或隐形渡河技能**。

路径计算需要读取起终格，不能只用当前 `stepCost(unit, destinationTerrain)`。Dijkstra、可走范围、AI 预测路径及玩家实际移动共用同一费用函数。

### 4.2 状态与行动

- 水上状态由单位当前格是否为 `water` 推导，不单独保存易失配的 `embarked` 布尔值。
- 在一次允许的移动中可以入水再上岸；攻击时按最终站位结算，路过水面不会留下额外的“湿身”惩罚。
- 已经消耗的移动力、行动机会、混乱/溃败规则正常保留；上下水不会刷新行动。
- 河岸两侧仍按通常的敌方控制区规则限制移动；ZOC 不因隔着一条陆水边界消失。
- 可走格必须考虑当前占位。不会因为全部兵种能下水就允许两支单位重叠。
- 停留水上本身不增加溺亡、随机漂移或额外军粮消耗；这些不是用户此次要求，首版不添加。

## 5. 水上攻击、防御与技能

### 5.1 统一伤害修正

建议首轮调参值：

- 水上攻击系数 `waterAttackMultiplier = 0.75`。
- 水上承伤系数 `waterIncomingDamageMultiplier = 1.25`。

这是“攻击降低 25%，承受兵力伤害增加 25%”。若一定要用等效防御表述，相当于防御系数 `1 / 1.25 = 0.8`，不能把“防御下降 25%”和“承伤增加 25%”混写。

对一次合法的兵力伤害，先计算不含水上状态的基础伤害，再应用：

```text
伤害 = 基础伤害
     × (施伤单位当前在水上 ? 0.75 : 1)
     × (受伤单位当前在水上 ? 1.25 : 1)
```

基础伤害仍可包含兵力、武力/智力、士气、兵种关系、陆地地形、天气、侧击与随机幅度。水上系数各乘一次，不能在基础函数和命令执行阶段重复叠加。

基础伤害计算保留现有普通攻击/火计/反击的 20/12/10 下限及原有内部取整顺序，避免为了水战改动全部陆地伤害基线；这里只移除本文件明确列出的旧水上特例。基础值计算完毕后，再乘水上修正，最后取整为实际伤亡、保留正伤害至少 1 人的保护，并限制到目标剩余兵力。乘过水上系数后不得重新套用 20/12/10 下限，否则低兵力水上单位的攻击惩罚会被覆盖。反击必须先算完整的未施加水上状态的反击基础值，再将水上系数乘一次，不能从已带水上系数的普通攻击函数重复叠加。

在其他条件相同、远离取整和兵力封顶时：

| 来源位置 | 目标位置 | 相对同条件基础伤害 |
| -------- | -------- | ------------------ |
| 岸上     | 岸上     | 1.0000×            |
| 岸上     | 水上     | 1.2500×            |
| 水上     | 岸上     | 0.7500×            |
| 水上     | 水上     | 0.9375×            |

水对水的双方都同时承受攻击减弱和防御降低，因此净伤害不是简单再减 50%。UI 要分别显示两个状态来源，不能只写一个含糊的“水战弱化”。

### 5.2 所有兵种一视同仁

当前 `naval` 的独占水格、低水格费用和水上 0.82 承伤保护全部移除。该既有类型如果仍在编制中，可以保留其名称和基础射程/移动力，但不会自动免除任何水上惩罚。

首版不新增“水军技能”“渡河熟练度”“提督免罚”“战船升级”等水战专属门槛。后续若要增加，必须作为新设计决定，不能借着复用旧代码悄悄保留。

### 5.3 岸水之间的攻击与反击

- 正交方格的距离采用现有曼哈顿距离。斜俯视只是表现方式，视觉上贴近不等于逻辑相邻。
- 近战单位在相邻岸水格之间可以攻击；不会要求先下水才能攻击水边敌人。
- 弓兵等远程单位可攻击正常射程内的水上目标，水上单位也可用同一射程攻击岸上目标。
- 首轮不新加视线遮挡、舰船朝向或跨岸特殊范围规则；水域本身不阻断射线。若后续扩展 LOS，应全局设计，不能只限制岸上打水上。
- 反击按受击后剩余兵力重新计算，来源和目标角色互换后再次读取各自格子。水上反击同样有攻击惩罚，岸上反击水上目标同样得到目标承伤修正。
- 反击仍须满足存活、未混乱/溃败、射程等普通条件，不产生反击链；跨岸不额外禁止反击。

### 5.4 六种计策的明确处理

| 计策              | 水上来源/目标的处理                                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 火计 `fire`       | 合法射程内可对水上单位使用；对兵力伤害应用同一水上攻防修正。移除原 `water → 0.35` 特例，以免与统一弱防冲突；雨天/风天、森林等其他火计修正保留并记录 |
| 伏击 `ambush`     | 仍需来源站在森林且满足未移动等条件，因此来源本身不会在水上；合法范围内的水上目标承伤 ×1.25                                                          |
| 落石 `rockfall`   | 仍需来源站在山坡；合法水上目标可受击，承伤 ×1.25；函数需读取战场/位置，不再完全忽略目标水上状态                                                     |
| 鼓舞 `rally`      | 不造成兵力伤害，士气效果和合法性不受水上伤害系数缩放                                                                                                |
| 混乱 `confuse`    | 不造成兵力伤害，成功率与普通条件保持；不把“攻击下降”误套成智力下降                                                                                  |
| 劫粮 `raidSupply` | 作用是军粮变化，按已有合法条件执行；不乘兵力伤害系数，也不产生新船只资源                                                                            |

火计的水上规则是本游戏的简化战斗设计，不宣称历史或物理模拟。界面应直接显示预计伤害与修正来源，让玩家不会误以为水上天然免火。所有计策的“可用性、目标筛选、预测、实际执行、AI 估值”必须引用同一规则，不能只改普通攻击。

### 5.5 预览与日志

攻击预览至少显示：来源兵种与地形、目标地形、范围合法性、伤亡区间、可能反击及双方水上修正。移动到水格的确认/预览要显示“下水后攻击 −25%，承伤 +25%”。

示例：`弓兵 → 水上步兵：射程内；目标水上承伤 +25%；预计伤亡 120–153；目标无法反击：超出近战范围。`

示例数值只是文案样例；实际数值由共用预测函数计算，不能写死。测试预览不消耗 RNG、不改变战斗状态。

## 6. 战术 AI 与每日调度

### 6.1 AI 必须理解风险与收益

1. 可达性与移动费用直接复用玩家路径服务，不再把非 `naval` 的水路标成不可达。
2. 位置评分同时计算水上攻击减弱与受到岸上火力的风险；不能只因为水路短就把全部部队排进河里。
3. 有便宜渡口/陆桥时优先比较安全路线，遭堵或需要迂回时可以主动下水；不能以无限高惩罚事实上禁止 AI 水战。
4. 岸上弓兵应识别水上目标，近战单位应识别可跨岸攻击和反击。
5. 水上单位知道何时上岸、继续过河或保护撤退，不在岸边进出反复耗回合。
6. 营地防守、队形、接敌与绕路半径按新模板和目标重标定，不能原样保留旧图的固定 4/8 格启发式。
7. 取消墙/门的 AI 专门路径和目标分支，保证不会追逐本版不存在的设施。

AI 只可使用本方可见信息和同一资源/行动预算。路径缓存要随地形版本、占位变化和单位状态失效，不能复用到已经移动的敌军。

### 6.2 与每日世界的接口

集成轨道统一日历；本轨道提供“推进一场战斗一个战斗日”的确定性接口。按 [L 轨日序](02-calendar-and-logistics.md) 先处理当日早晨指令与合法出发，再冻结活跃战斗集合。玩家操作完成或 AI 完成该场当日回合后，世界统一提交战果与补给、推进在途队伍、处理到达，然后只增加一次战略日期。新战场从新日开始正常行动。

- 多场同时进行的战斗不会逐场累加战略天数。
- 当日抵达的军队在下一日获得正常行动，不在到达当日多打一轮。
- 自动战斗在游戏里也按此接口推进，不能直接调用一个全战斗循环把其他事件冻住。
- 单独的性能/平衡测试可使用完整自动结算包装器，但该包装器不得作为绕过世界调度的 UI 命令。
- 玩家浏览、拖动镜头、打开 Wiki 或等待输入均不推进战斗日。

战斗输出只包含已发生的单位损失、消耗、胜负及归属引用，由战略层一次性记账。不得同时在战斗结束和世界日提交时扣两次粮。

## 9. 验收与测试

### 9.1 地图与路径自动测试

- 四样板 × 至少 20 固定种子：都是 480 格，营地/部署合法，所有目标有合法路径，生成不依赖渲染或系统时间。
- 每个水战样板至少验证一条完全经过水域的通路和一条陆地/渡口替代通路；特殊窄谷样板另测，不伪称都有两条路线。
- 对当前六种兵种测试陆→水、水→水、水→陆、水→山坡以及峭壁不可达；护卫 2 点移力可上岸。
- 检查路径预算恰好够、差 1 点、被占位阻断、跨岸 ZOC、入水再上岸、地图边界不环绕。
- 测试原 `naval` 不再独占水格，不存在额外水上抗伤或水格速度减免。

### 9.2 战斗公式自动测试

- 在相同兵力/属性/RNG、无其他地形修正下，四种岸水组合的未取整伤害为 1、1.25、0.75、0.9375 倍。
- 对六类来源与六类目标至少覆盖普通攻击矩阵；保留兵种克制，水上系数只叠加一次。
- 低兵力取整、击杀封顶、反击后剩余兵力、混乱/溃败不能反击等边界正确。
- 无水上状态的陆地对陆地攻击/火计/反击保留原伤害下限；低兵力下水后伤害仍按水上比例降低，不被再次应用基础下限覆盖。
- 近战跨岸相邻可打；弓兵岸上打水上、水上打岸上、水上打水上均按原射程可用；超距拒绝不改变状态。
- 火计/伏击/落石的合法水上目标都应用承伤修正；火计无旧 0.35 水上特例；来源地形仍约束伏击/落石。
- 鼓舞/混乱/劫粮不被错误地缩放为兵力伤害；水域不隐藏新增技能门槛。
- 伤害预测与实际随机边界一致；预测、切换语言、悬浮格子均不消耗 RNG。

### 9.3 AI、联调与保存

- 固定“岸上弓兵可打水上敌军”“唯一可达路为水路”“渡口堵塞但可绕水”“水中护卫需撤回岸边”场景，AI 能做合法且有意义的选择。
- 记录重复进出水域、无法解释的等待、守营不动、桥头堵塞；任何永久循环或死锁都是失败。
- 全部新图确认没有 wall/gate、城门耐久、攻城技能、城市内外阶段和旧墙体胜利条件。
- 新 schema 无旧城墙防御字段；相同条件的各城民兵基础武力均为 40；营地有无目标标记不改变同底层地形的费用或伤害，确保旧 `fort` 减伤已退出。
- 水上单位移动后保存，重载后继续攻击/上岸，结果与不中断运行一致；非法格子、重复占位、错误 mapVersion 应拒绝。
- 两场同日战斗加一支途中军队：两场各推进一日后战略日只提交一次；所有补给账本各扣一次。

### 9.4 体验与性能

初步体验目标：对等开放野战首次交火中位数 2–4 日、总长度中位数 6–15 日；河网和山谷单独报告。暂保留普通战斗 30 日上限作为起点，突袭期限须与新的路途/补给分开计量。目标不是把所有战斗强行拉长。

保留双方 10 单位的自动结算 p95 <50 ms 作为对照目标，记录样板/种子/机器/预热/样本数。每日推进、路径查询也单独测；若性能不达标，先优化确定性缓存或预算，再明确报告调整建议。

与渲染轨道一起在人类实际操作中验证：24×20 真有侧翼和阵形空间，水域不是纯贴图，能看出哪些单位在水上、下水的攻防后果和岸上攻击机会。常规/大字号、中英、1366×768、1920×1080 与手机宽度下，选择/预览不能依赖微小像素。

**交付报告必须分列：** 已完成规则、尚未完成规则、测试数量与结果、性能数据、四样板截图、人工体验结论及剩余调参。图片生成完成不能代替水战实现完成，旧版通过记录也不能作为新规则的验收证据。

### 10.2 初始候选确认的集成缺陷（历史记录，现已修复）

下列复现记录来自初始候选；修复结果和当前回归测试见 10.4 与[实施台账](../../implementation-status.md)。

1. **驻军民兵可令开战编组出现重复单位 ID。** `src/v03/engine.ts:153-190` 先按兵种把军官编组，再在 `openBattle` (`:471` 起) 把未由军官带领的剩余驻军追加为新的 `infantry` 编组；`rosterFromGroups` 用 `prefix + troopType` 作为 ID。因此目标城同时有带兵步兵将领和额外民兵时会生成两个相同的步兵 ID，membership 映射也会互相覆盖；`createTacticalBattle` 会因跨 roster 的重复 ID 拒绝创建战斗。已复核的复现条件为 seed `481516`、曹操方濮阳出征下邳 700 兵，并给下邳增加带 1,000 兵的步兵将领和 100 名未编组民兵；抵达时抛出 `defender roster contains duplicate unit IDs.`。验收：覆盖“有/无步兵将领 × 驻军多于/少于已带兵总数”，每个将领和民兵只计入一次、编组 ID 唯一、保存校验通过，并能正常开战与结算。
2. **非玩家双方的 AI 战斗可被本地玩家发命令。** `applyV03BattleAction` (`src/v03/engine.ts:1228-1244`) 只把“攻方是否为玩家”映射为 attacker/defender，再与保存的 `playerSide` 比较。非玩家交战的 `playerSide` 也被构造为 defender，于是该比较通过；`applyBattleAction` 只再验证单位属于该边，没有验证该阵营是否玩家。已由运行时复现确认非玩家战斗可接受玩家的待命命令。验收：双方都非玩家时任何 `battleAction` 都原子拒绝且状态不变；玩家为攻方/守方时只可命令玩家一侧；AI 战斗仍由日推进自动处理。
