## 1. 产品定位与已定范围

**v0.3 是独立发展的三国策略游戏，不再以复刻 BAYE 为目标。** 暂沿用《Hegemony of the Three Kingdoms》的产品名称。既有代码是可复用基础，旧规则、旧平衡和旧存档不构成新设计的兼容约束。保留真实的代码来源、许可和致谢记录；不把历史来源改写为原创。

| 决定 | 玩家已确认的规则                                              | 实施要求                                                                                             |
| ---- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| D1   | 先核对真实城市位置与距离，建立粗略历史行军基准，再区分单位    | 直线、路线估计、速度假设分开；取消旧稿汉中—长安硬性 30 日下限，按有依据的估计计算                    |
| D2   | 内部按日；推进 1 日、1 旬或到下个事件；每月 30 日             | 统一绝对日、可暂停事件、月度结算一次                                                                 |
| D3   | 24×20 战场                                                    | 长宽各翻倍，共 480 格；不能只扩大 CSS 画布                                                           |
| D4   | 借鉴空间层次、地图操作和可读性；中式水墨、高视角斜俯视        | 地形逻辑与斜俯视投影分离，原生命中测试、小地图与近景阅读一起交付                                     |
| D5   | 正式太守辖城自治；君主本城直辖                                | 人事任命决定治理权限，不只增加数值加成                                                               |
| D6   | 玩家保留任免；治理模式只在结算边界变化                        | 本计划采用月界生效初案，防止任免刷新行动/切换微操                                                    |
| D7   | 可以手动战斗                                                  | 城市经营权与战术指挥权分开                                                                           |
| D8   | 太守报告可执行量、缺口、最早日期；玩家选择缩减或等待          | 不静默减少征调或出兵数量，不即时转移资源                                                             |
| D9   | v0.3 不需要旧存档                                             | 不做 v1/v2 迁移或双规则运行；新存储命名空间，识别并拒绝旧档，不删除已有浏览器数据                    |
| D10  | 完全没有攻城；有人人可参与的水战                              | 无破门、城墙通行、攀墙、攻城兵器、市街阶段；所有单位下水降低攻防，岸对水按射程可攻击，无水军技能门槛 |
| D11  | 30 日战斗时限到达后，剩余兵力较多的一方控制战场；平手判守方胜 | 使用战斗中的存活总兵力比较；全歼仍由即时战斗结果处理，平手明确由守方控制                             |

不再要求用户重新回答这些决定。开发期间新发现的实质取舍单独记录，不能把已批准决定重新标成待定。

## 2. 本轮共同默认值与边界

- 维持 24 城、现有两个剧本和双方各最多 10 个战斗单位作为首轮规模；城市历史锚点由 G 轨校正，剧本仍可为游戏化历史场景。
- 现有六类兵种可暂保留，`naval` 不再获得水域准入或免罚特权。是否以后精简兵种另议，本轮先保证一致水战。
- 战略水路是否连通来自路线数据；战术单位能进入水格不意味着大地图可任意渡海或绕过不存在的路线。
- 单位移动、攻击距离采用逻辑方格。高视角投影不改变四邻接、射程、ZOC 或路径费用。
- 全部敌我势力执行相同的时间、资源与城市权限成本。随机性由存档 RNG 控制，查询、预览、美术不消耗游戏 RNG。
- 外交、任免、君主本城内政、太守的征调/出征指令及所有玩家部队的手动战斗是不同权限。
- 无正式太守且非本城的城市，暂由地方班底自治维持，等待任命；不因“太守空缺”自动开放额外直辖微操。这是 D5 的补充初案，不是玩家额外提出的历史制度。
- 临时演员、地图样例和美术原型可提前做；最终地图底图必须等真实地理布局确定，不能锁定旧示意坐标。

## 3. 接口 C1：地理与道路（G → L / R / A）

| 数据            | 必含内容                                                                                           | 使用者不得做的事                                       |
| --------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| CityGeography   | `cityId`、历史指代、时期、经纬度、证据等级、来源、位置误差说明                                     | 用标签偏移代替地理位置；把现代同名城默认当古城         |
| RouteDefinition | `routeId`、两端、路径/走廊、直线 km、路线 km 区间及名义值、道路类别、方向/季节参数、来源等级、版本 | 把直线长度叫历史道路长度；再重复叠加已经包含的山地减速 |
| TravelProfile   | 单位组合/运输任务的速度、路段限制与修正、参考条件                                                  | 让玩家和 AI 采用不同公式；使地图缩放影响时间           |
| AtlasGuide      | 地理投影、范围、山河骨架、城市锚点、标签偏移、路线层                                               | 让 imagegen 输出决定规则地理                           |

G 轨的距离表和明确算法为唯一距离基准。L 轨实现相同计算并提供 UI 可调用的纯预览函数；R/A 只读取。历史不确定性与游戏中采用的名义 ETA 分开显示。

## 4. 接口 C2：日历、行程与命令（L ↔ V / B / R / I）

| 对象            | 最少字段/含义                                                                                            |
| --------------- | -------------------------------------------------------------------------------------------------------- |
| Calendar        | `absoluteDay` 从剧本首日 0 开始；日期从它派生，30 日/月、12 月/年                                        |
| DailyResolution | 正在处理的日、阶段、稳定顺序游标、当日活跃战斗 IDs、已完成 IDs；支持日内存档                             |
| Journey         | ID、所属势力、关联指令、来源/目的地、路线版本快照、出发日、分段进度、人员/兵力、携带/预留/交付账本、状态 |
| OfficerLocation | 明确且互斥的城内、途中、战斗、俘虏/非活动状态；不能用一个 `cityId` 假装同时在两处                        |
| Estimate        | 准备等待、去程天数、预计到达日、补给明细、计算依据、拒绝原因；预览不改状态                               |
| DomainEvent     | 稳定 ID、日期、类型、参与实体、来源命令；报告/通知从事件派生，避免重复交付                               |

命令发起时引用实体 ID 与状态版本，规则层重新验证，不信任 UI 的已选列表。失败保持原状态、库存、额度与 RNG 不变。

## 5. 接口 C3：太守权限（V → L / UI / I）

- `Administration`：本城/正式自治/临时自治、现任与待生效太守、生效月界、代理人、治理修订号。
- `Requisition` / `CampaignDirective`：所需数量/规模、期限、候选方案、缺口、玩家确认、预留、在途执行引用、取消/完成状态。
- `Capability` 查询用于 UI 提示；相同规则在命令执行时强制校验。不要暴露可随意伪造的 `isGovernor` 布尔量。
- 太守只能调度自己的辖城动作，不能凭内部身份修改外交、获得免费资源或刷新属下行动。
- 中英拒绝原因包含具体缺口和日期；报告由规则事件产生，不能每次重新渲染再跑一遍 AI。

## 6. 接口 C4：战斗（B → L / R / A / I）

- `BattleMap`：尺寸 24×20、稳定 map/version/seed、480 格地形、部署区、营地/战术目标、进攻方向；地形为可行走的 plain/forest/hill/water 与不可通行的 cliff，不含城墙、城门或攻城阶段。营地是普通地形上的目标，不自带城防倍率。
- `BattleState`：战场 ID、起始绝对日、当前战斗日、当前阶段、双方军队引用、单位坐标与状态、供给、结果。
- `BattleSnapshot` / 规则查询：可走格、路径费用、可攻击目标、伤害预览、水域修正、地形说明；显示层不得自行推断合法性。
- 水上状态由**当前逻辑格**推导，不创建需玩家购买/装配的船装备门槛；上岸后自动恢复相应陆地规则。
- 推荐调参初值是水上攻击 ×0.75、承受兵力伤害 ×1.25；具体作用顺序、计策和反击见 [B 轨](04-battlefields-and-water-combat.md)。此数值不是玩家指定值，需测试与记录。
- L 负责全局日期和资源账本；B 负责一个战斗日的规则推进，不能独立快进全世界或重复扣粮。

## 7. 接口 C5：投影和资源（R ↔ A）

首轮共用提案规格：逻辑方格不变；地面菱形为 128×64 世界单位；投影 `((x−y)×64, (x+y)×32)`。偏移和镜头缩放由 R 管理。逻辑宽高与纹理像素数没有等价关系。

| 类型             | 运行资源提案    | 锚点（纹理归一坐标） |
| ---------------- | --------------- | -------------------- |
| 地面材质         | 512×512，可拼接 | 按 R 轨 UV/地块合同  |
| 地物             | 512×512 RGBA    | `(0.5, 0.84)`        |
| 单位             | 256×256 RGBA    | `(0.5, 0.86)`        |
| 通用水上运输标记 | 256×128 RGBA    | `(0.5, 0.6)`         |

像素只是编码建议，内置生成工具的输出必须实际检查后再裁切/优化，不能假定提示词保证尺寸。所有资源有稳定 key、版本、源文件、锚点、占位范围、变体、许可证/来源记录和缺失回退。原型与最终资源分目录；不要求绘画决定水格边界。

R/A 可以先用该规格共同做一组带单位与水格的样板；若发现投影/锚点需要改变，只改一次合同并同步双方，不能各自悄悄偏移修图。

## 9. 共享文件的唯一负责人

I 轨拥有 `types.ts`、命令总入口、`App.tsx` 总装配、保存封装、公共本地化索引、根 README、package/scripts 等共享文件。其余轨先提交领域接口和独立模块，跨轨接线由 I 合并。

现有 `campaign.ts`/`battle.ts` 是集中式文件；实施第一步先由 I 建立领域模块边界。未拆出前，一个共享源文件只给一个写入者。不同 agent 同时改这些文件不算真正的并行。

改变任何 C1–C6 合同时，更新本文件并列出受影响轨、字段、原因和兼容假设，相关 owner 确认后再继续。用户已批准的大方向不因此重新请求确认。
